HOW TO RUN

Download it. Run it.
Make it yours.

This project is meant to be downloaded from GitHub and run on your own computer. There's no sign-up, and nothing to pay for to look around. Do the steps in order and copy each command exactly. You'll have it running in about ten minutes.

THE FAST PATH — START HERE

Hand it to your coding agent

Most people installing this already work with Claude Code, Cursor, Copilot or something like them. That is the quickest way to do it, and it is what this page is written for: an agent can follow these steps as well as you can. Open your own project in your agent and paste this in.

What to expect. It should stop and ask you twice: once about what may change and what your goal is, and once before it spends anything on a practice run. Those two are the decisions that stay yours. Everything else it can read out of your codebase. At the end it should hand you SELF-IMPROVE-CHECKLIST.md with the (agent) boxes ticked and the (you) boxes listed — those last ones are the GitHub settings, the billing and the judgement calls, and an agent ticking them on your behalf is the failure this file is shaped to prevent.

Prefer to do it yourself, or want to understand what the agent is doing? The rest of this page is the same thing, one step at a time. There are also shorter prompts for single jobs — running the website, adding a page — in Ask your AI assistant.

What you're downloading

The repository has two halves. Each one is set up in one obvious place, so you can change either without touching the other.

Frontendconsole/

The website you're reading, including the ten-step installer on the Console page. It's served by one small file, console/server.mjs, and needs no database. The header and footer each live in their own file in console/partials/.

Backendharness/

The part that does the real work. When a new AI model comes out, it asks that model to improve your project, checks the change, and hands it to you as a pull request. You set it up with one file, project-adapter.yml.

Before you start

Install these first. Each one is free.

  • Node.js 22.11 or newer. Go to nodejs.org and download the version labelled LTS. Use the default options in the installer.
  • A code editor with a built-in terminal, such as VS Code or Cursor. If you use an AI coding assistant, open the project in it.
  • Git, from git-scm.com. Optional: you can download a ZIP instead.
  • For Part 2 only: a GitHub account, and an API key from at least one AI lab. Anthropic or OpenAI is a good first choice.

Part 1 — Run the website

About five minutes. At the end, this site runs on your own computer.

  1. Download the project

    With Git: open a terminal and paste this.

    git clone https://github.com/Chrisfoz/self-optimisation.git

    Without Git: open the repository on GitHub, click the green Code button, choose Download ZIP, and unzip it somewhere you'll find it again, such as your Documents folder.

  2. Open the folder in your editor

    In VS Code or Cursor, choose File → Open Folder… and pick the self-optimisation folder. Then choose Terminal → New Terminal. That terminal is already in the right folder, and every command below goes there.

    To check, the folder should contain package.json, README.md, console and harness.

  3. Check Node is installed

    node --version

    You should see v22.11.0 or a higher number. If you see "not recognized" or "command not found", install Node (see Before you start), then quit your editor completely and open it again.

  4. Start the website

    npm start

    You should see a line like console listening on :3000. Leave this terminal open, because closing it stops the site.

  5. Open it in your browser

    http://localhost:3000

    Paste that into your browser's address bar. When you're done, click in the terminal and press Ctrl + C to stop the site.

  6. Optional: run the checks

    npm test

    This runs the project's own tests, and they should all pass. If you change something and a test fails, the output tells you what broke.

That's Part 1. The website runs locally. Next, change how it looks (see Make it yours) or set up a real project (Part 2).

Part 2 — Set up your own project

The harness doesn't improve this repository. It goes into another project of yours and improves that one. Try it on a project you don't mind experimenting with. By default, each change arrives as a pull request for you to merge. Automatic merge is opt-in: once you trust the runs, you can let changes that pass every gate merge on their own.

This uses real API credits. Every suggestion is a real call to an AI lab, billed to your key. Set a monthly spending limit on your lab's billing page first.

Way A: the installer

Answer ten questions in your browser and download the files. Best if you'd rather not edit settings files by hand.

Way B: the terminal

Copy the harness in and answer the same questions in the terminal. It can also do a practice run on your computer.

Way A: the installer

  1. Open the installer

    With the website running from Part 1, open localhost:3000/console. It may say GitHub sign-in isn't configured. That's expected on your own computer, and every step still works.

  2. Work through the ten steps

    Choose your AI labs and models, the files that may and may never be changed, your test command, and what "better" means for your project. The panel on the right shows the exact files it will generate.

  3. Download the setup files

    In the last step, check the files and download self-optimisation-setup.tar.

  4. Unpack them on a new branch of your project

    In a terminal inside your project:

    git checkout -b self-optimisation-setup
    Mac / Linux
    tar -xf ~/Downloads/self-optimisation-setup.tar
    Windows PowerShell
    tar -xf $HOME\Downloads\self-optimisation-setup.tar

    Look at the files before you commit them. Change the path if your download went somewhere else.

  5. Follow SELF-IMPROVE-README.md

    The download includes this file. It lists the API keys to add as GitHub secrets (Settings → Secrets and variables → Actions) and how to do the first run. Beside it is SELF-IMPROVE-CHECKLIST.md — the same list as Before you let it run below, rendered with your own branch and secrets, and shaped to be ticked off rather than read.

    One GitHub switch is off by default, and it's easy to miss. On your project's repository (not your account), open Settings, click Actions in the left sidebar, then General, and scroll to Workflow permissions at the bottom. Choose Read and write permissions, tick Allow GitHub Actions to create and approve pull requests, and click Save. The Pull Requests section under Settings → General looks similar but is the wrong page. Reload the page afterwards to check the tick stayed. You don't need a GitHub personal access token.

Setting up more than one project? Use + New in the installer's Projects list. Each project keeps its own draft, and Copy settings from carries over the labs, models, cadence and budget you already chose. The repository, tests, files, goal and automatic merge are set for each project separately.

Want the installer to connect to GitHub directly? Then it can read your repository and open the setup pull request for you. That needs a GitHub App of your own, which is more advanced; see console/DEPLOYMENT.md.

Way B: the terminal

  1. Make sure your project uses Git

    The harness puts each attempt on its own branch. If your project isn't a Git repository yet, run this in its folder: 

    git init

  2. Copy the harness folder into your project

    Drag the harness folder from the download into your project's top-level folder, or from a terminal inside your project:

    Mac / Linux
    cp -r ../self-optimisation/harness ./harness
    Windows PowerShell
    Copy-Item -Recurse ..\self-optimisation\harness .\harness

    These assume both folders sit side by side. Change the path if yours don't.

  3. Add your API key

    The harness keeps its keys in harness/.env.harness.local — never in .env. Most real applications already have a .env of their own (a database URL, mail credentials, their own model key), and an earlier version of these steps told you to copy over it, which destroys that file. Keeping the two apart is the point, not a workaround: your web server has no reason to hold nine labs' API keys, and the harness has no reason to hold your database's service-role key. The two names cannot collide, whatever your project already does.

    node harness/cli/init.mjs writes this file for you in the next step, and never overwrites one that already exists. To create it now, by hand:

    Mac / Linux
    cp harness/.env.harness.example harness/.env.harness.local
    Windows PowerShell
    Copy-Item harness\.env.harness.example harness\.env.harness.local

    Open the file you created and paste your key after the matching name, such as ANTHROPIC_API_KEY=sk-ant-…. Leave the other lines blank.

    Put the keys in the .local file, not the .example one. The two names exist to keep them apart: harness/.env.harness.example is tracked by git and holds placeholders only. Filling in the tracked one is how keys reach a commit, and it has happened.

    Now prove git is ignoring it. Do not assume — a .gitignore that lists .env, .env.local and .env.production.local individually, which is a common shape, does not cover .env.harness.local. Run this; it must print a matching rule, and print nothing at all from the second command: 

    git check-ignore -v harness/.env.harness.local
git ls-files harness/.env.harness.local .env .env.harness.local

    If the first prints nothing, add .env.* (no leading slash, so it matches inside harness/ too) and !.env.harness.example to your .gitignore and run it again before you go any further. Anyone who sees your key can spend your money.

  4. Answer the setup questions

    node harness/cli/init.mjs

    Press Enter to accept a suggested answer. It writes project-adapter.yml (all the settings in one file), .claude/agents/improve.md and review.md (the two brief files), the GitHub workflow, and SELF-IMPROVE-README.md.

  5. Fill in the two brief files

    Open .claude/agents/improve.md and review.md and replace every [bracketed placeholder] with real answers about your project. This is the most important step: the AI only knows what "better" means if you say so here. Your AI assistant can draft it (see Ask your AI assistant), but read what it writes.

  6. Check your settings

    node harness/scripts/validate.mjs

    This catches mistakes before they cost anything, like a path that doesn't exist or a placeholder you missed. Fix what it lists and run it again until it passes.

  7. Do a practice run

    node --env-file=harness/.env.harness.local harness/scripts/rehearse.mjs

    This runs the whole loop on your computer, on a new local branch. It normally waits for a newly released model, so the first run usually finds nothing and stops, which is expected. To try a model right away: 

    node --env-file=harness/.env.harness.local harness/scripts/rehearse.mjs --models claude-opus-5

    It never pushes, opens a pull request or merges.

    Start with one model. Each model you name is sent every file it may edit. On a large project that is 250,000 tokens or more per model before it writes a word, and a model that runs out of room is asked again with the whole input resent. The first practice run on a large web app, with six models, used just over 2 million tokens. Each run's docs/generations/gen-NNN/attempts.json shows what every model spent, so read it before adding more.

  8. Optional: run it on GitHub automatically

    When a practice run looks good, the generated workflow can run the same loop on GitHub. The steps are in the install guide, Steps 5 and 6, including the Workflow permissions switch GitHub leaves off.

    Merge the setup branch first. A practice run cuts its branch (agent/gen-001) from your setup branch and saves its record back onto the setup branch. If you merge the practice run's pull request into main first, the harness arrives without that record, and the setup pull request still looks unmerged. Merge setup into main, then the practice run into main.

Before you let it run: a finished installation

Every item below went wrong at least once in a real installation. Tick them all before the monthly run starts, whichever way you installed.

You do not have to tick these here. The installer writes this same list into your project as SELF-IMPROVE-CHECKLIST.md, rendered with your own branch, your own test command and the exact secrets your installation needs — so it can be ticked in a pull request and read back later. Each item there is tagged (agent), settled by a command, or (you), settled in a browser or a billing console. A coding agent should finish the first kind and hand you the second; it should never tick a (you) item on your behalf. What follows is the same list in prose, for reading before you install.

  • Everything is on your default branch. The harness, your project-adapter.yml, both brief files and the workflow are merged into the branch your project deploys from, usually main. project.default_branch in the settings file names that same branch. node harness/scripts/validate.mjs warns if it doesn't match your repository's default.
  • Your keys are nowhere in git. git ls-files harness/.env.harness.local .env .env.harness.local prints nothing, and git check-ignore -v harness/.env.harness.local prints a matching rule. Check harness/.env.harness.example still holds placeholders too — that one is tracked, and filling it in is how keys reach a commit.
  • GitHub has a secret for every lab the run calls. On your project's repository: Settings → Secrets and variables → Actions. One for each lab you watch, plus the labs of the models you chose to write and review changes. Add SENDGRID_API_KEY too if you want the email. SELF-IMPROVE-README.md lists exactly which.
  • Workflow permissions are saved. Read and write, with Allow GitHub Actions to create and approve pull requests ticked, on Settings → Actions → General. Reload the page to check the tick stayed.
  • Every lab has credit, not just a key. A key can be valid on an account with no payment method. The practice run's reachability check is the first place that shows up (for example 402 billing_not_configured), and the run carries on without that lab. Set a monthly spending limit with each lab you use.
  • The email works, if you want it. A notify: section in project-adapter.yml with a sender address your email service has verified, the key as a secret, and the workflow regenerated with node harness/cli/init.mjs --from-adapter --force. Without the notify: section the workflow has no email step at all.
  • You know what a merge will deploy. If your host deploys your default branch on every push (Railway, Vercel and Netlify usually do), merging a generation's pull request puts it live. Check whether your host waits for your CI to pass first. On Railway that is each service's Wait for CI setting.
  • You know where to see progress. After every run, docs/generations/index.html is rebuilt and committed: every generation, newest first, with the change in plain words, whether it shipped, is waiting for your review, or why it didn't (each failed attempt and its reason), and what it cost. Pull requests waiting for you are at the top. Open it in a browser from your checkout. GitHub shows HTML as source, so use GitHub Pages to browse it online. docs/generations/REPORT.md has the same records as metrics.
  • You know when it runs. On the 1st of each month, or straight away from Actions → Self-improvement loop → Run workflow. Leave the models box empty to wait for a new release, or name models to run on them now.

Who does what in a run, and how much you hand over

A run is not one model doing everything. Four seats do the work, and the gates that decide whether it ships are not models at all. All of it is set in roles: in project-adapter.yml, so you can see the whole arrangement in one screen.

SeatWho fills itWhat it doesSet in
Suggest
Rotating		 Whichever watched lab shipped something new Reads your brief, your committed goal and the run history, and proposes one change. This is the seat that makes a new release worth something: every run gets the newest reader in the field. providers.watched decides who is eligible; the seat itself is not pinned
Implement
Pinned		 A model you chose Writes or refines the exact edits when the suggesting model's own edits need work. It may change only files your allowlist permits, and it does not get to change the rules. roles.implement.model
Review
Pinned		 A model you chose, ideally from another family Reads the actual edits with fresh context and returns a verdict. An unreadable or self-contradictory approval is treated as a rejection, not a pass. roles.review.model — this seat fails closed, so it is never auto-picked
Rank
Optional		 Auto-picked from a different family, or pinned Only called when more than one lab proposed in the same run: it orders the proposals before any of them is implemented. Left unset, the run picks a model from a different family than the implementer, because a judge prefers its own family's prose. roles.rank.model, or null to auto-pick
The gates
Deterministic		 No model at all The path allowlist, the diff guard and your own test command check the work regardless of which model wrote it. These are the checks a model cannot argue its way past. constitution and your project's test command

A pinned model's lab does not have to be one you watch — watching is what the release detector looks at, pinning is a separate choice. But that lab's API key still has to be a repository secret, or the run fails when it reaches that seat.

How much you hand over is three separate dials

They are easy to confuse, so here they are apart. Each one has a conservative default, and you can turn any of them up later without touching the others.

  • How big a change may be. context.ambition: focused keeps every run small, earned (the usual choice) starts small and allows a bigger swing after a clean streak, ambitious allows one from the start.
  • Who presses merge. By default a change that passes every gate stops at a pull request and waits for you. Automatic merge is opt-in, and switching it on is itself a change you have to approve — after a practice run has passed. What happens after a merge is deployment.verify_strategy.

    This is one choice, made once, at install time (constitution.approval_class), and it is rendered into the generated workflow as ordinary YAML: only one of the two paths exists in your workflow file, so which one you got is answerable by reading it. No run decides this for itself — which matters, because the branch a run works on is a branch a model has been writing to. To change it later, edit project-adapter.yml and regenerate with node harness/cli/init.mjs --from-adapter --force.

    How you find out. If you configured notify:, every run emails you. When a change is waiting for your decision the email is headed 📋 WAITING FOR YOU, not "not merged", and it carries the pull request link and the workflow run link near the top — the decision should take one tap from your inbox. Without notify: there is no email, and the run history page at docs/generations/index.html lists anything waiting on you at the top instead.
  • Whether a seat can be earned. roles.promotion.implement_after_self_implemented_approvals lets a rotating model that has had its own edits approved and kept that many times take the implement seat from your pinned model, for as long as it holds the record. Omit it, or set 0, and no seat ever moves — that is the default. The review seat is never promoted: it is the gate, and a gate is not a prize.

What it costs, and what that buys

Each generation is paid for in API credit, and each one that ships is a change someone didn't have to make by hand. So the useful question isn't "how many tokens?" but "what did each merged change cost, against the time it would have taken a person?" Count your own review of the pull request in that time too. The harness only saves time if you trust what it sends.

Tokens are not dollars

Most tokens a run uses are input: the files each model reads. Input costs a fraction of output. The first real installation, a large web app with about a million characters of editable code, gave these figures (September 2026, at each lab's list price):

What happenedTokensRoughly
Each suggesting model reading the project250,000–380,000 inputDepends on the lab's price and tokenizer
A practice run with six suggesting models2.0 millionMost of it input, spread across six labs
A failed run: one suggester, then the implementer ran out of room twice1.06 millionAbout $5 for the Claude Opus 5 part
A run that shipped: one suggester wrote its own edits, tests passed, one review, pull request opened393,000Under $1 for the Claude Opus 5 review, plus the suggester reading the project
The same, but the implementer writes the changeAbout 0.8–1 millionAdd roughly $2–3 of Opus 5 input per implementation attempt on a project this size

Model prices change often, so check each lab's pricing page for your own estimate. Divide your editable code's character count by four for a rough token count per model.

What actually wastes money

  • Runs that spend and ship nothing. A seat whose account has no credit, or a model that runs out of output room. The harness now checks every fixed model before paying for a suggester, and turns a crashed run red. Read the email or the run, not just the tick.
  • Many suggesters at once. Each one reads the whole project. Start with one or two.
  • A wide editable area. Every file in constitution.allowed_paths is sent to every suggesting model. List the files that matter, not whole folders' worth.
  • Thinking you didn't need. Reasoning models spend output tokens thinking, and that counts against their limit. For the implementer, which follows a proposal someone else wrote, roles.implement.effort: medium is often enough.
  • The most expensive model where a cheaper one will do. The top tier can cost twice as much per token as the next one down. The digest email only needs a mid-tier model (notify.digest_model).

Keeping it bounded

  • A spending limit at every lab you use. This is the only hard monthly ceiling. The harness can't see your balance.
  • A token cap per generation (budget.max_generation_tokens), sized to your project: about a quarter of your editable characters per suggesting model, plus the same again for the implementer and reviewer. A run that would go over stops before calling anyone.
  • The monthly schedule. The loop runs when a lab releases a new model, checked once a month, not continuously.

Two savings are built in. The implementer is shown only the files the proposal names, and can ask for more (it used to receive every editable file). On Anthropic models, what it rereads on a retry or refinement comes from the prompt cache at a tenth of the input price. The first write costs a quarter more, once. Each run's attempts.json shows cacheReadTokens when caching saved something. To turn caching off: roles.implement.prompt_cache: false.

If something goes wrong

"node" or "npm" is not recognized / command not found

Node isn't installed, or your terminal was opened before you installed it. Install the LTS version from nodejs.org, then quit your editor completely and open it again.

Windows: "running scripts is disabled on this system"

PowerShell is blocking npm. Run this once, then try again:

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Or switch your editor's terminal to Command Prompt or Git Bash.

"EADDRINUSE" when running npm start

Something else is using port 3000, possibly an earlier copy of this site you didn't stop. Close that terminal, or use another port as shown in Make it yours.

The installer says GitHub sign-in isn't configured

That's expected on your own computer. Every step and the download still work (Way A). Connecting to GitHub needs a GitHub App of your own; see console/DEPLOYMENT.md.

The digest email is only a few terse lines

That is the fallback, sent when the model that writes the plain-language email can't be reached. Harness copies from before 17 September 2026 always sent it, because the email scripts never loaded the labs. Copy harness/ in again from this repository. If you're up to date, check the key for your notify.digest_model's lab.

A practice run drops a lab with "402" or "billing"

The key works, but the account behind it can't be charged. Add a payment method or credit on that lab's billing page. The run carries on with the other labs. Checking a key by listing models won't catch this, because listing is free.

validate warns that default_branch doesn't match

Setup was probably run while you were on a setup branch, and older harness copies saved that branch as the default. Set project.default_branch to the branch you deploy from (usually main) and run node harness/cli/init.mjs --from-adapter --force.

A page says "Not found", or a change doesn't show up

The server only serves pages listed in PAGES in console/server.mjs, and it loads every page once at startup. After changing a website file, press Ctrl + C and run npm start again.

npm test fails straight away with a strange file name

Your Node version is probably too old. Run node --version, and if it's below 22.11, install the current LTS.

The practice run says "no new models" and stops

That's expected. The first time it sees a lab, it records that lab's current models and waits for a new one. Add --models claude-opus-5 (or another model your key can use) to try one straight away.
