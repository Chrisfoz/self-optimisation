YOUR REPOSITORY. YOUR RULES.

Set up your improvement loop

Configure, review, rehearse. Then choose when it runs.

    01 / CONNECT

    Choose your repository

    Sign in with GitHub to select a repository granted to this console’s GitHub App. Or prepare a configuration before connecting.

    Checking GitHub connection…
    Connect GitHubManage repository access ↗

    Connect your account, grant access to selected repositories, then choose a project. Connecting alone does not change any files.

    02 / LABS & KEYS

    Choose who gets a turn

    Watch one or more labs. You also need keys for the models in your pinned seats, even if their labs are not watched.

    Add API keys directly on GitHub. This console never accepts or stores model API keys. It checks secret names, not values or available credit. A rehearsal tests the real provider calls.
    Open GitHub secrets ↗

      Organisation and environment secrets are not counted by this check. Add repository secrets for this installation.

      03 / SEATS

      Pin the models you trust

      The suggester rotates. These roles stay on the model IDs you choose. Pick from the list below or type any model ID your account can call; availability is verified during rehearsal.

      Use model IDs your account can call. Display names and subscription names are not API model IDs. A model ID whose lab this harness cannot recognise still works — name its lab beside it, and nothing in the harness needs changing to run a model released this morning.

      04 / STAGES & TESTS

      Give the change a real test

      The full loop includes discovery, proposals, ranking, implementation, review, guard checks and tests. These stages work together; the console cannot switch off the safety gates.

      Review, path protection and tests are always required. Email notification is not configured by this installer; outcomes are available in GitHub and the Runs view.

      05 / BOUNDARIES

      Define the space for change

      Unmarked files cannot be edited. The harness, workflow, briefs, package scripts and environment files stay protected.

      Always protected by this installer

        06 / META-GOAL

        Tell it what better means

        This becomes your committed project goal and the brief each model reads. Be specific about the people using your project and the outcome they need.

        07 / CADENCE

        Choose when to check

        The schedule checks whether a new model has appeared. Your first installation is always manual until a rehearsal passes and you merge the activation pull request.

        Release-check schedule

        08 / APPROVAL

        Decide what happens after the gates

        Your initial rehearsal always opens a pull request. Any automatic merge choice takes effect only through a separate activation pull request.

        After activation

        09 / BUDGET

        Put a limit on each generation

        Fan-out controls how many detected models may propose. The token cap bounds model requests across the generation. Neither is a dollar estimate.

        Model usage is billed by your providers, and GitHub Actions usage is subject to your GitHub plan. Reserve estimates can stop a run before it finishes; increase the budget only after inspecting the record.

        10 / REVIEW & REHEARSE

        Inspect it before it runs

        Generate the actual adapter, workflow and briefs. A setup pull request also includes the harness files needed to run in your repository.
