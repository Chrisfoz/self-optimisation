    Which labs get a seat live

    Each new frontier model gets one turn to propose an improvement. Pick only the labs you hold a key for — two is a normal start, nine is not required.

    Your keys never reach our servers. Each one is encrypted in this browser tab with your repository's own public key and sent straight to GitHub Actions Secrets. We can't read them, and we have nothing to lose if we're breached.

    Who implements, who reviews live

    The suggesting seat rotates — whichever lab above just shipped gets it. These two don't. They stay on models you picked, so a brand-new model can propose freely while a known quantity checks the result.

    Which stages run

    Every stage you switch off is a job the generated workflow simply doesn't contain. Two can't be switched off at all.

    What "better" means here live

    This becomes the agent's brief, and it is sent whole as the suggestion stage's entire system prompt. It's the one thing no template can guess — and the field most likely to get a two-word answer, so the prompts below are deliberately specific.

    Written to .claude/agents/improve.md

    How often it runs

    The design's premise is that a model release is the trigger, not the calendar — the schedule is just how often we check whether one has happened.

    Written to on.schedule.cron in the workflow live, and mirrored into cadence.schedule_cron saved, not yet wired

    Who says yes

    Independent review and the guard run either way. This decides only what happens after they both pass.

    How wide one run may fan out live

    A ceiling on how many newly released models one run may ask. We won't guess what that costs — lab pricing moves on its own schedule and a guess presented as a number is worse than no number. What we will do is tell you the moment a key stops working.

    4

    What this run could ask, this time

    4 proposals, 1 implementation, up to 3 refinements

    The spend is yours, on your own keys — we never see it. What we do see is whether a call succeeded. If a lab returns "invalid key" or "insufficient credit," it shows up on the Runs tab the moment it happens, not buried in a log.

    Review, merge, rehearse, then switch on

    Four files, one pull request, nothing on your default branch until you merge it. Merging switches nothing on — the workflow arrives with no schedule in it at all.

    FileChangeWhat reads it

    1. Open a pull requestRead the diff. The workflow in it can only be run by hand — there's no schedule in the file yet.
    2. Merge itGitHub will only let a workflow be triggered once it's on your default branch. That's why rehearsing comes after merging, not before.
    3. Rehearse onceWe trigger a single run and show you what came back — the proposal, the review, and whether it would have shipped.
    4. Switch on the scheduleA second one-line pull request adding the monthly trigger. Offered only once a rehearsal has passed.
    In plain terms. Once switched on, this can change 3 files in your repository once a month and open a pull request for you to merge. It can never touch 4 protected paths, can never change more than 50 files at once, and can never edit its own instructions.
