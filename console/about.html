THE IMPROVEMENT LOOP

A new model starts it.
Evidence decides what leaves.

A run begins when a watched lab ships something — or when you name a model yourself and start one. What it proposes is shaped by your goal and by the questions the last runs left open. Either way a proposal is only the beginning: every change must pass the checks you configured.

01 / A RELEASE ARRIVES

Watch the labs you choose

The first check saves a snapshot of every watched lab's catalogue. Later checks compare against it, so a new model is noticed rather than announced. A manual campaign lets you put a chosen model to work without waiting for one.

02 / ONE CHANGE IS PROPOSED

Incremental by default

The new model gets your brief, your committed goal and the run history, and proposes a single change. Small and steady is the default; a clean streak earns a bigger swing. When several labs propose, the harness ranks them before anything is implemented.

03 / EVIDENCE DECIDES

Check the change, not the pitch

A pinned reviewer reads the actual edits with fresh context. Rejected work can be refined within your attempt limit. Protected paths and failing tests stop promotion outright — those are not arguments a model gets to win.

04 / THE RUN IS REMEMBERED

And the next one starts there

Every outcome is written down, including the runs that shipped nothing, and the next model reads it back. Every few generations a review looks across that history for the pattern nobody named and records the questions it raises — yesterday's evidence choosing tomorrow's ambition.

Whatever passes every gate waits for you as a pull request; merging automatically is opt-in. Which seat each model takes, and how much of that you hand over, is set in one file — who does what in a run.

THE CURIOSITY LOOP

Fixing is not the same
as getting curious.

A loop that only repairs what it can already see gets very good at small repairs. The second half of the design turns a project's own history into questions, and questions into work. Four of its ten components run today.

Running

A goal it may argue with

You commit to one goal when you install. A model can argue it is wrong, and the reviewer rejects a correct, tested change that moves away from it — but nothing in a run may edit it.

Running

Questions, not just fixes

The periodic review names what it cannot explain, not only what it can. Those open questions go into the next proposal prompt, numbered, so a model can cite the one it is answering.

Running

Agreement becomes work

When models from different labs raise the same concern, it is escalated to you. Accept it and it becomes a queued work order a later run is handed and has to report back on.

Running

What the run actually saw

Test output, deployment checks and model probes are fed back as observations, so the next question can be about how the project behaves rather than only about how it reads.

Six components are specified and not built: the question ledger, three-way run modes, the spike (a run that produces a sourced document instead of a diff), external research, memory consolidation and retrospective scoring. They are deliberately gated on one cheap experiment — if the questions this harness already writes are never cited by a later run, the rest should not be built at all. The specs, the gate and the reasoning are all in the repository: docs/curiosity ↗.

WHAT TO EXPECT

Useful work.
Honest limits.

The harness runs today

The generation loop has been exercised with real model calls and GitHub Actions. The console uses the same configuration and workflow generator as the command-line installer.

Setup depends on your deployment

GitHub sign-in requires a configured GitHub App. You can prepare and download configuration without signing in. API keys are entered on GitHub, never in this console.

It costs real money, so judge it per merged change

Every generation is paid for in API credit, mostly for the models reading the code. On a large web app, a generation that shipped used 393,000 tokens: under $1 for the review, plus the suggesting model's reading. Runs where a pinned model writes the change cost a few dollars more. The fair comparison is the cost of each change that ships, including your review of it, against the time a person would have spent. Runs that spend and ship nothing are the real waste, and the harness now stops the most common ones before paying for them. What it costs

Better models do not guarantee better changes

Your test coverage, your committed goal and your project brief still decide most of it. Six of the ten curiosity components are specs rather than code, and none of this is a promise of autonomous research: it proposes one change at a time and asks you to judge it.
