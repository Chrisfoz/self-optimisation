Self-Optimisation

Your repository gets a second opinion every time the field moves.

When a lab ships a new frontier model, it gets exactly one turn to propose one improvement to your project — and four independent gates it has to pass before a single line reaches you.

The objective

Software gets better when someone with fresh eyes reads it. Frontier models now arrive every few weeks, each with genuinely different judgement — and every one of them is a reader who has never seen your code before. The problem has never been asking them. It's that acting on the answer unsupervised is reckless, and reviewing every answer by hand is work you won't keep doing.

So this is a governed loop rather than an assistant. The trigger is a model release, not a calendar tick. The proposing seat rotates to whoever shipped most recently, while the reviewing seat stays pinned to a model you already trust. Changes arrive as exact edits to files you explicitly allowed, applied all-or-nothing, checked by an independent reviewer, a guard, and your own test suite. What reaches you is a pull request and a short email explaining it.

The trigger is a release, not the calendar

A run happens because there is a new mind to ask. Nothing new shipped this month? Then nothing runs, and nothing is spent.

An agent can argue with a rule, never change it

Protected paths are enforced against the real diff. A model that thinks a rule is wrong can say so — and it takes three models across two labs agreeing before that reaches you as a decision.

Every run writes down what it tried

Including the ones that shipped nothing. The next run reads it back, so the same dead end doesn't get proposed twice.

One run, end to end

Everything between the release and the pull request is automatic. The four boxed stages are the reason that's safe to say.

What you set up, once

The console asks nine questions and writes four files to your repository as a pull request. There's no terminal, no YAML to hand-write, and no step where an API key of yours reaches anyone but GitHub.

  1. Connect your repository we read your file tree, nothing else
  2. Choose which labs get a seat pick two, or all nine
  3. Choose which stages run review and the guard can't be switched off
  4. Mark what may change and what must never be touched
  5. Say what "better" means here the one thing no template can guess
  6. Set how often it checks monthly by default
  7. Decide who says yes a pull request, or automatic merge
  8. Set what it may spend with the per-run cost shown first
  9. Review the diff, then rehearse once the schedule stays off until it passes
