Self-Optimisation

Your repository gets a second opinion every time the field moves.

We bet on the curve. Harness the power of Frontier labs, we leverage their insights to continuously improve your project. Every insight is captured and acted upon systematically. This ensures that your project evolves in step with the latest advancements. When a lab ships a new frontier model, it gets exactly one turn to propose one improvement to your project — and four independent gates it has to pass before a single line reaches you.

The objective

Software gets better when someone with fresh eyes reads it. Frontier models now arrive every few weeks, driving benchmarks on performance, each with genuinely different judgement — and every one of them is a reader who has never seen your code before. The problem has never been asking them.

This is a self improvement governed loop rather than an assistant. The trigger is a model release. The proposing seat rotates to whoever shipped most recently getting the benefit of incremental improvements, while the reviewing seat stays pinned to a model you already trust. Changes arrive as exact edits to files you explicitly allowed, applied all-or-nothing, checked by an independent reviewer, a guard, and your own test suite. What reaches you is a pull request and a short email explaining it.

Including the ones that shipped nothing. The next run reads it back, so the same dead end doesn't get proposed twice.

One run, end to end

Everything between the release and the pull request is automatic. The four boxed stages are the reason that's safe to say.

Who sits in which seat

Four roles run in every generation. Only one of them rotates — that's the whole design. The other three stay on models you picked and can vouch for, so a brand-new model gets to propose freely while nothing it says reaches your repository without a known quantity checking it first.

🆕 The suggesting seat — rotates

Whichever watched lab just shipped something new. Reads a curated context pack, not your whole codebase, and proposes one specific change. This is the only seat that changes hands, and it changes hands because a release happened.

🔧 The implementer — pinned, your choice

Turns the proposal into an exact edit — or steps aside when the suggesting model wrote a usable patch itself. Defaults to Claude Opus, and can be pointed at any lab's model instead.

🔍 The reviewer — pinned, your choice

A fresh pass with no memory of the pitch. Configured separately from the implementer, so the two can be different models — and an unparseable verdict counts as a rejection, never an approval.

✅ The gates — not a model at all

Your own test suite and the guard. They don't care which model wrote the change or how convincing its reasoning was. Green or it stops.

Picking a pinned model from a lab you aren't watching is a normal thing to do — reviewing with Claude while watching only OpenAI, say. Watching is about where proposals come from; pinning is about who you trust to check them. The installer works out which API keys that combination actually needs and wires them all, rather than assuming the two lists are the same.

What it starts asking, once it has a history

This part is designed, not built. Everything above describes a loop that improves what it can already see. The gap it leaves is that a loop like this only ever answers questions someone thought to ask — it gets steadily better at fixing, and never gets curious.

The proposed second pass changes what accumulates between runs rather than what happens inside one:

  1. Every proposal carries an open question asked from the first run — "none" is a fine answer — and the answers pile up where the next run can read them
  2. Corroboration is counted, not assumed a question only earns prompt space once independent models from different labs arrive at it separately
  3. Every tenth-ish run looks for the pattern not what happened, but what it meant — and, newly, what the project still doesn't understand about itself
  4. Occasionally a run spends itself investigating producing a sourced document instead of a diff, when the honest answer is "nobody here knows yet"

A repository with no history has nothing to be curious about, and that's correct rather than a degraded mode — the first several runs are the ordinary loop, quietly filling the record that makes the tenth one worth having. The reason to build it at all is the bet above: if models keep getting better at long tasks, the limit stops being can it write the change and starts being did anyone point it at the right question.

The bet this depends on

None of this works if frontier labs stop shipping, or stop improving. That's an external bet, not something this loop controls — so rather than assert it, here is the actual release cadence, live from an independent tracker this project doesn't maintain.

Releases by Lab Over Time — via AI Release Tracker · an independent third-party site, not affiliated with this project.

Cadence is only half of it. The other half is whether each new model is actually more capable — and the clearest public measure is METR's 50% task-completion time horizon: how long a task takes a skilled human, at the length where an AI agent succeeds half the time. A longer horizon means a model can carry more of a change on its own before it needs a person.

These are quoted rather than embedded because METR offers no embeddable chart — so treat the numbers as a dated snapshot and follow the link for the current set. METR's own caveats are worth carrying with them: confidence intervals are wide, the trend is sensitive to which tasks are in the suite, and measurements above 16 hours are unreliable on the current one.

This is why the trigger is a release rather than a calendar tick. If the curve flattens, this loop quietly stops proposing anything — which is the correct behaviour, not a failure. Nothing here depends on the bet paying off this month; it depends on it being worth asking each time someone ships.

What you set up, once

The console asks ten questions and writes four files to your repository as a pull request. There's no terminal, no YAML to hand-write, and no step where an API key of yours reaches anyone but GitHub.

  1. Install on your repository GitHub's own picker — one repo or several, nothing granted beyond what you select
  2. Choose which labs get a seat pick two, or all nine
  3. Choose who implements and who reviews pinned models, defaulting to Claude Opus — set separately, so they can differ
  4. Choose which stages run review and the guard can't be switched off
  5. Mark what may change and what must never be touched
  6. Say what "better" means here the one thing no template can guess
  7. Set how often it checks monthly by default
  8. Decide who says yes a pull request, or automatic merge
  9. Set how wide it may fan out and see the moment a key stops working
  10. Review the diff, then rehearse once the schedule stays off until it passes
