Privacy policy

Last updated 21 August 2026

Draft, not yet in force. The console described here isn't built. This policy is written alongside its design so that the privacy decisions get made before the code does, rather than after — see console/DESIGN.md §2.2. It becomes binding on the day the console accepts its first user, and not before.

The short version

  • We never receive your API keys. They're encrypted in your own browser and sent straight to GitHub.
  • We store the minimum to show you your own repositories — your GitHub username, which repos you set up, and how each run went.
  • Your configuration lives in your repository. You can read it, change it, and delete it without us.

What the console is

A web page that asks you some questions about your project and writes the answers into your own GitHub repository as a pull request — a configuration file, a scheduled workflow, and two instruction files. That's the entire product. It doesn't run your code, host anything for you, or sit between you and anyone else.

Your API keys

The console asks for API keys from the model labs you choose to use. Those keys are worth real money, so they're handled so that we can't touch them even if we wanted to.

When you paste a key, your browser fetches your repository's public encryption key from GitHub, encrypts your key locally, and sends only the encrypted result to GitHub's Actions Secrets. The readable key exists in your browser tab and in GitHub's encrypted storage. It is never sent to us, never logged by us, and never passes through a server we control.

What this means practically. If we were breached tomorrow, your API keys would not be part of it, because we don't have them. It also means we can't help you recover a lost key — go to the lab that issued it.

Signing in with GitHub

Signing in only tells us who you are — your username, name and avatar, enough to show you your own work. It grants no access to any repository by itself. That access is a separate step, described next, and you can sign in without ever taking it.

Installing the app on your repositories

To let the console read or write a repository at all, you install it as a GitHub App — the same mechanism GitHub itself provides for tools like this, not a broad "log in with GitHub" grant. Installing shows you GitHub's own picker: all of your repositories, or only the ones you choose. The console can never see or touch a repository you didn't select, because the access GitHub hands us is limited to exactly that list — not a restriction we promise to honour, one GitHub enforces on our behalf.

The app asks for four permissions, fixed and declared up front rather than requested piecemeal, so you see the whole set before you install:

  • contents: write — to read your repository and open a branch with your configuration on it
  • secrets: write — to store the encrypted keys described earlier
  • actions: write — to add the scheduled run, and to trigger the one-off rehearsal you ask for
  • metadata: read — basic repository information GitHub requires every app to have
What we hold, in plain terms. A GitHub App has its own private key, generated when the app is registered and kept only in our server-side secret storage — never in a repository, never in a browser. We use it to ask GitHub, moment to moment, for a token that works for an hour and only on the repositories you've installed the app on. That's a credential of ours, not one of yours we're holding — a materially different thing from a stolen password or a leaked API key, since it can't be used against any account beyond what's actually installed, and it expires within the hour either way.

Removing access is a single action on GitHub's side, not ours: Settings → Applications → Installed GitHub Apps, where you can drop one repository or uninstall entirely. It takes effect immediately, and every token already issued for that repository stops working — there is nothing further to revoke with us, because we never held a token of yours to begin with.

Your account, and what we store

Signing in creates an account. It holds your GitHub username, display name and avatar — enough to show you your own work and nothing more. Your email address stays with GitHub and with our authentication provider; we don't copy it into our own records.

Alongside it we keep five short lists, all of them about you and visible only to you:

  • the repositories you've set up, and a copy of the configuration file sitting in each one
  • a history of runs — when, what happened, which model proposed it, a link to the pull request, and whether a lab flagged an invalid key or a billing problem
  • any rule your models have disputed and that's waiting on your decision
  • a record of what we wrote to your repository and when
  • your account itself

The configuration copy is a cache, not the original: the file in your repository is the real one, and it stays there whatever happens to us.

Every row is locked to your account by the database itself, not just by our code — there is no shared or public way to read any of it. The record of what we wrote to your repository can be added to but never edited or deleted, including by us, because an audit trail that can be rewritten isn't one.

We never store API keys, your source code, the diffs a model proposed, or the prompts sent to any lab. The database physically rejects a write that looks like it carries a credential, so a bug on our side fails loudly rather than quietly collecting keys.

This data is held in Supabase's Sydney region (ap-southeast-2). We don't use analytics, advertising, or third-party trackers, and we set no cookies beyond keeping you signed in.

What your code is shared with — read this one

The console doesn't read your source code beyond your file and folder names, which it needs to show you the tree where you choose what may be edited. But the harness it installs does something you should understand before you turn it on.

Once running, the harness sends parts of your repository to the model labs you selected — the files you marked editable, your project's instructions, and a summary of recent runs. This happens inside your own GitHub Actions, using your own API keys, under each lab's terms and data policy. We are not a party to it and never see any of it. If your repository contains anything you wouldn't send to a third-party API, mark it as never-editable, or don't install this.

Other people's services

  • GitHub stores your repository, your encrypted secrets, and your workflow runs, under GitHub's own privacy policy.
  • The model labs you choose — Anthropic, OpenAI, Google and the rest — receive whatever the harness sends them, under their own terms. You pick which ones, and you can pick none.
  • Supabase hosts our database and handles the GitHub sign-in described above, in their Sydney region.
  • An email provider, if you switch on the run digest, sends that email using a key you supply. We don't operate it and don't receive the mail.
  • AI Release Tracker supplies the release-cadence chart embedded on the "what it does" page. That chart is an iframe served by aireleasetracker.com, so loading that page makes a request to them and they may see your IP address and browser, under their own privacy policy. No console page sends them anything about you, your account, or your repositories. It is the only third-party embed on any of these pages, and it appears on that one page only — the console itself embeds nothing.

Removing it

Three steps, none of which need us: revoke the app's access in your GitHub settings, delete the four files it added, and delete the secrets it stored. The harness stops running the moment the workflow file is gone.

Deleting your account removes everything listed above, including the cached copy of your configuration. Your repository is untouched by that — the files and the run history in it are yours and always were.

Children

The console is a developer tool for people managing their own code repositories, and isn't directed at children.

Changes

If this policy changes in a way that affects what's collected or who sees it, the change lands in the repository's git history like everything else, and the date at the top of this page moves. The history is public, so you can see exactly what changed and when.

Contact

Open an issue on github.com/Chrisfoz/self-optimisation. Privacy questions in the open are useful to everyone reading later.
