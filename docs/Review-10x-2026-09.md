# Review and a 10x plan — 2026-09-04

A second outside read of the project, written two days after the
2026-09-02 review was adopted and most of its Tier 0 and Tier 5 shipped.
It answers one question the first review did not set out to answer:
**what would make this harness ten times more valuable against its stated
objective, a portable improvement harness, and in what order.**

Every claim about the code was checked against the code on `main` at
`9e8f545`. `npm test`: 505 checks, all passing, on Linux, in five seconds.
No model call was made. Line counts below are `wc -l` on the day.

**Status of this document:** a review and a proposed plan. Nothing in it
is adopted until the owner moves it into `WORKPLAN.md`, the way the
previous review's §6 was moved. The reasoning stays here.

---

## 1. What the project is, in one paragraph

A model release is the trigger. Every newly released frontier model is
asked, over the same context, for one improvement to a target project.
A judge from another family picks one proposal. A pinned model, or the
proposer itself, turns it into search-and-replace edits applied
all-or-nothing against an allowlist. A pinned reviewer with fresh context
approves or rejects, and rejection loops back up to three times. CI then
runs a frozen-path guard and the project's own tests, opens a pull request
by default, and emails a digest. Every run writes a record, and the next
run reads it. The whole loop is real, tested with faked model calls, and
chained into one generated GitHub Actions workflow by an `init` command.

## 3. Findings

Numbered so the plan can refer to them. F1 to F11 in
[`Review-SWOT-2026-09.md`](Review-SWOT-2026-09.md) still hold where not
ticked; these continue the numbering.

### F12. The harness has never made a real model call

This is the finding everything else waits on. `carrotgame`, the reference
implementation, runs its own scripts, not `harness/`. The one end-to-end
run of `run-generation.mjs` against a real adapter had no API key and
produced a `no-proposal` record (`Portable-Harness-Design.md` §10,
revision note). `tests/e2e/full-loop.test.mjs` fakes the three model
calls. The 2026-09-02 review made no call either. So the 505 checks prove
the state machine and the git plumbing, and prove nothing about whether
a provider's real response parses, whether the prompts as assembled fit a
real window, or whether the edit format survives contact with a 2026
model. Everything the harness now records, including cost, ambition and
seat promotion, has been exercised only on fixtures.

*Cheap to fix. Nothing in the plan below should start before it is.*

### F13. The tests are outside the loop

`evaluation.test_commands` is baked into the generated workflow and read
by nothing at run time (`project-adapter.example.yml`, closing section).
The refine loop is implement → review → implement → review, and the
project's own tests run only after the loop has exited and pushed a
branch (`workflow.yml.tmpl`, the `tests` step). A change the reviewer
approved and the tests reject is simply held, the generation is lost, and
the implementer never sees the failing output. The reviewer never sees it
either: `review.mjs` takes a prose `testDescription`, not a result. This
is the single largest yield lever in the code, and the cheapest.

The design note that keeps `test_commands` out of the runtime is about a
different risk, that a run should fail on what CI ran rather than on a
list in a file. Both can be true: run the commands inside the loop for
*feedback*, and keep CI's baked copy as the *gate*. That is principle 11,
enforce every rule twice, applied to tests.

### F14. The implementer is a single completion

Stage 2 is one call that returns edit blocks (`orchestrator.mjs`,
`implement()`). It cannot read a file outside the source bundle, grep,
run a command, or look at a compiler. The 2026 systems the project cites
in `learning/07-whats-actually-new.md` are all agentic; the provider
router has no tool-use path at all (`grep -rn tool_use harness/` returns
nothing). The paper's own §3.6, a bounded executor in an isolated
workspace with command policies and execution logs, describes what is
missing. Governance does not require a single-shot executor. It requires
that every write pass the allowlist, which `applyEdits()` already
guarantees whatever produced the edits.

### F15. There is no sandbox

Tests and evaluator plugins run on the CI runner, in the same job that
holds every lab's key. The keys reach only three steps by `env:`, which
is correct, but `actions/checkout` persists the job token into
`.git/config` for the whole job (the template sets no
`persist-credentials: false`), and the test process has the network.
`evaluators.mjs` says in its own header that "Node has no such sandbox".
The paper's §9 controls (isolated execution, network deny-by-default,
ephemeral credentials) are unbuilt. On a repository with outside
contributors this is the first thing a security reviewer will ask about.

### F16. Context does not scale past a handful of files

`context.strategy: scoped` has no implementation; `init` warns the user
to their face when they choose it. `buildSourceBundle()` sends every
editable file in full, the allowlist is exact paths only
(`editablePatterns: []` is reserved and unused), the fence language falls
through to `html`, and the test-name extractor knows `test`/`it`/`describe`.
A Python, Go, Java or Rust project with more than a dozen source files is
outside what the harness can run today. This is the portability blocker,
and `WORKPLAN.md` 2.2 correctly waits on a second project to decide its
shape, which is a circular wait: no second project can be rehearsed
without it.

### F17. Portable means "GitHub Actions, with `gh` installed"

Three modules shell out to the `gh` binary (`pull-requests.mjs`,
`rollback.mjs`, the generated PR step). Fourteen files read GitHub-shaped
environment (`GITHUB_OUTPUT`, `RUNNER_TEMP`, `github.token`). There is no
CI abstraction, no GitLab or generic template, no way to run the guard,
tests and PR chain locally. `run-generation.mjs` runs on a laptop, but
the eight steps around it exist only as YAML. Principle 2 says build the
rehearsal door with the loop; the loop has one, the chain does not.

### F18. Install is copy-a-folder, with no validation

No package, no action, no schema. `validateAnswers()`, which
`console/DESIGN.md` §2.1 calls "the whole value of the thing", does not
exist. An adapter can name an editable path that is not in the repo, a
frozen path that overlaps an editable one, or a brief file still full of
`[placeholders]`, and the first run is where it finds out.
`init --check-upgrade` compares a version string; there is no upgrade.

### F19. One change per cycle, and N−1 proposals are still discarded

The 2026-09-02 review said so (§2, §5) and 5.12 keeps the losers' text
now. Nothing implements them. Cost scales with the number of proposers,
output does not, and no generation ever compares two implementations of
the same repository. The record has no signal that could tell whether the
ranker picked well.

### F20. The harness cannot measure its own improvement

Every check fakes the model. A change to a prompt, a rubric or the edit
format is validated by the same fixtures it was written against. There is
no corpus of target repositories, no way to run one generation against
each and count what applied, passed and was approved, and so no way to
know whether any change to `harness/` made it better. Principle 22b
applies to the harness as much as to the product: the harness measures
what it can reach, and today it reaches only itself.

### F21. The documentation outweighs the code and is hand-synced

585 KB of markdown against 508 KB of harness source. Status lives in
`README.md`'s table, `ARCHITECTURE.md`'s diagram and prose,
`Portable-Harness-Design.md`'s revision log, and `WORKPLAN.md`, kept in
agreement by hand with a stated tie-break. Two of the four largest
files design things that are largely unbuilt, and the largest still
opens with "planning only, nothing described here has been built yet",
which stopped being true weeks ago. The honesty is
exceptional and worth keeping; the volume is a bus-factor and onboarding
cost, and principle 23 says the status half should be generated.

### What is strong, restated briefly

The previous review's Strengths section stands. Two things have improved
since: the loop now records cost and reads the owner's verdict back, and
the seats are described and warned about on every run. The code quality
is high, the pure-logic/thin-CLI split is real, and the record every run
writes is richer than anything in the cited literature. The problem is
not the quality of what is built. It is that what is built is a very
good governance layer around a 2024-shaped executor that has never run.

## 4. Where 10x comes from

"Ten times" needs a denominator. The value of a portable improvement
harness is the product of four factors, and today's figures for each are
either unknown or one:

| Factor | Today | What 10x means |
|---|---|---|
| **Reach** — the repository shapes it can run on | one: small HTML/JS, exact-path allowlist, GitHub Actions | any language, thousands of files, glob allowlists, two CI systems, one-command install |
| **Yield** — kept changes per generation | unknown; n=1 on a different codebase | measured on a bench; tests feed the refine loop; candidates compete |
| **Magnitude** — how much a kept change matters | tactical by construction (F14) | an executor that can iterate against tests can ship structural change that passes |
| **Trust** — evidence and blast radius | zero real runs; no sandbox | fifty real generations across five repositories; execution isolated from credentials |

The multiplication is honest only if each factor is measured before and
after, which is why the bench (§5, Phase 5) is not optional and not last.
Reach and Trust can plausibly move an order of magnitude. Yield and
Magnitude are more likely two to three times each, and the bench is what
will say.

Two constraints the plan keeps, because they are what makes this harness
different from an interactive coding agent:

- **Governance stays.** Allowlist on every write, guard in CI, a review
  that fails closed, a pull request by default. The plan makes the
  executor stronger and the sandbox real; it never widens what an agent
  may write.
- **The release clock stays as the novelty trigger.** It is the
  project's one defensible novelty. The plan adds a second, explicit
  trigger for work the loop already knows it owes (accepted escalations,
  regressed dimensions, open questions), and records which trigger ran.

## 5. The plan

Six phases. Phases 0 and 5 bracket the rest; 1 to 4 are ordered by how
much each unblocks. Written in `WORKPLAN.md`'s format, with a *done when*
line per item that is a fact rather than a judgement.

### Phase 0 — prove it runs (one week)

- [ ] **P0.1 — A real generation through `harness/`.** A scratch
  repository, a filled adapter and briefs, two lab keys, one campaign
  generation on a current model. Fix whatever breaks. (F12)
  *Done when:* a `gen-001/attempts.json` with `spend.estimatedCalls: 0`
  is committed to a public example repository, and the workflow run that
  produced it is linked from `README.md`.
- [ ] **P0.2 — `harness rehearse`.** One local command that runs the
  whole chain the workflow runs: detect or campaign → probe → preflight →
  improve → guard → tests → a diff and a record, on a local branch, no
  CI, no PR. This is the developer loop, the install check, and the
  first half of the CI abstraction in P3.2. (F17)
  *Done when:* the e2e test drives the chain through this command rather
  than by calling each library in sequence.
- [ ] **P0.3 — Adapter schema and `harness validate`.** A JSON Schema for
  `project-adapter.yml`, and `validateAnswers()` as `console/DESIGN.md`
  §2.1 specifies: every allowed path exists, allowed and frozen do not
  overlap, `.github/**` is frozen unless overridden, brief files exist
  and carry no `[placeholders]`, every pinned seat's lab has a key name
  the workflow will inject. Run by `init`, by `rehearse`, and as the
  first step of the generated workflow. (F18)
  *Done when:* an adapter with an editable path that does not exist fails
  before any model is called, with the path named.

### Phase 1 — close the loop (three to four weeks)

- [ ] **P1.1 — Tests inside the refine loop.** After `applyEdits()` and
  before review, run `evaluation.test_commands` (read at run time; CI's
  baked copy stays as the gate). A failure goes back to the implementer
  as the correction, with the last 200 lines of output; the reviewer's
  prompt gains a `### Test result` section. Preflight already proves the
  baseline, so a red result is attributable. (F13)
  *Done when:* the orchestrator test shows a change that fails tests on
  attempt 1 and passes on attempt 2 with the failure text in the second
  implement prompt, and the reviewer prompt carries the pass.
- [ ] **P1.2 — Sandboxed execution.** `evaluation.sandbox: {kind: docker,
  image, network: none}` in the adapter. Tests, evaluators and (in P1.3)
  tool calls run inside it with the working tree mounted, no environment
  passed through, no network by default. `none` keeps today's behaviour
  and `validate` warns. Set `persist-credentials: false` in the
  template and pass the token only to the steps that need it. (F15)
  *Done when:* a test that reads `ANTHROPIC_API_KEY` or opens a socket
  fails inside the sandbox and the record says so.
- [ ] **P1.3 — Executor v2: an agentic implement stage.** A bounded tool
  loop over the existing router: `read_file` (any path), `search`
  (grep), `run_tests` (P1.1's command, in P1.2's sandbox), and `edit`,
  which is `applyEdits()` and nothing else. Provider files gain a
  `tools` body shape; a model whose provider has none falls back to
  today's single-shot path. Caps: tool calls per attempt, tokens per
  attempt (the existing budget), churn ceiling on the final diff. Every
  tool call is logged into `attempts.json`. (F14)
  *Done when:* the bench (P5.1) shows the approval-and-tests-pass rate on
  the same proposals with v1 and v2, and v2 is not worse on the focused
  repos and better on the ambitious ones.
- [ ] **P1.4 — The reviewer sees evidence, not prose.** The test result,
  the tool log, and the evaluator delta against the base branch, in the
  review prompt. Still one call, still fails closed.
  *Done when:* the review test asserts a green test result and a red one
  render differently and the verdict parser is unchanged.

### Phase 2 — context that scales (three weeks, overlaps Phase 1)

- [ ] **P2.1 — `context.strategy: scoped`.** Two passes. Pass 0 sends the
  repository manifest plus a symbol index and asks for the files that
  matter for this brief and goal; pass 1 sends only those in full. The
  symbol index comes from `universal-ctags` when present and a
  regex-per-extension fallback when not, so nothing new is required to
  run. The allowlist becomes glob-capable (fill the reserved
  `editablePatterns` slot). (F16)
  *Done when:* `init` stops warning, and a bench repository with more
  than 100 source files completes a generation under the token cap.
- [ ] **P2.2 — Language-agnostic indexes.** The test index and the
  runtime-evidence reader take per-ecosystem extractors (pytest ids,
  `go test -list`, JUnit XML alongside TAP), with the current regex as
  the default. The fence language comes from an extension map.
  *Done when:* the bench's Python and Go repositories show a populated
  test index and skipped-test names in runtime evidence.

### Phase 3 — a portable install (three weeks)

- [ ] **P3.1 — Publish.** An npm package (`npx <name> init`) and a
  composite GitHub Action (`uses: <owner>/self-optimisation@v1`) so a
  workflow pins a version instead of vendoring a folder. "Copy one
  folder" stays as the offline path. Upgrade is a tag bump. (F18)
  *Done when:* a fresh repository goes from nothing to a rehearsed
  generation using only the published package, in under fifteen minutes,
  timed.
- [ ] **P3.2 — A CI seam.** `harness/ci/` with `github.mjs`,
  `gitlab.mjs`, `local.mjs` behind one interface: outputs, temp dir, open
  a PR or MR, read its fate, the run URL. `gh` is replaced by the
  provider's REST API over `fetch` with the job token, so the binary is
  no longer a dependency. Templates per CI. (F17)
  *Done when:* the same adapter produces a working GitHub workflow and a
  working GitLab pipeline, and `rehearse` uses `local.mjs`.
- [ ] **P3.3 — Branch-protection-safe bookkeeping** (`WORKPLAN.md` 5.10,
  decided): a `harness/state` branch holds the snapshot, PR fates, report
  and runtime evidence; the generation's records ride its own branch.
  *Done when:* a rehearsal on a protected default branch completes with
  no failed push.
- [ ] **P3.4 — A runner image.** One container image with Node, ctags
  and the harness, used by both CIs and by P1.2's sandbox as the default.
  *Done when:* the generated workflow runs in it and the image is
  published from this repository's CI.

### Phase 4 — throughput and selection (three weeks)

- [ ] **P4.1 — Parallel candidates.** Implement the top K proposals (K
  from the adapter, default 2) in separate worktrees, run P1.1 tests and
  the evaluators on each, review each, open a PR for every one that
  passes or only the best by evaluator delta (adapter choice). Every
  candidate's outcome is recorded. This is what turns the fan-out into a
  search and gives the ranker a label. (F19)
  *Done when:* a record shows two candidates with different test and
  review outcomes, and `REPORT.md` prints ranker precision (how often the
  ranker's first choice was also the one that passed).
- [ ] **P4.2 — A backlog trigger beside the release trigger.** A
  generation may also start from a queued work order (C8), a themes
  review's open question with corroboration of two or more, an
  evaluator dimension that regressed, or an issue labelled for the
  harness. Runs on the pinned seats, on a cadence the adapter sets,
  never on a rotating model, and the record carries `trigger: release |
  backlog | campaign`. The release trigger is unchanged.
  *Done when:* a repository with no release in a month still ships a
  generation from a queued work order, and the index says why it ran.
- [ ] **P4.3 — The kept-change verdict** (`WORKPLAN.md` 5.4): PR labels
  `gen:good` and `gen:regret`, read back with the fate, counted in
  promotion precision.
  *Done when:* the report distinguishes kept-and-endorsed from
  kept-by-default.

### Phase 5 — evidence (starts in week 2, runs throughout)

- [ ] **P5.1 — The bench.** `bench/` with five target repositories at
  pinned commits, chosen to be different on purpose: a Python CLI (no
  visual surface, `verify_strategy: none`), a TypeScript service with
  more than 100 files, a Go library published to a registry, a Rust
  crate, and a documentation-only repository. Each has an adapter and
  briefs. `harness bench --models <list>` runs one campaign generation on
  each and prints one row per repository: proposal produced, edits
  applied, tests passed, review approved, tokens, wall time. This is the
  harness's own fitness function, and the thing every phase above is
  measured against. (F20)
  *Done when:* the table has been printed for `main` and for every
  branch that changes a prompt, a rubric or the executor.
- [ ] **P5.2 — Replay carrotgame's history** (`WORKPLAN.md` 4.3a, plus
  one question): run the harness's suggest and review stages against
  carrotgame's repository at each of its 18+ generation tags, and ask
  whether the harness's reviewer would have approved what actually
  shipped and whether its ranker would have chosen it.
  *Done when:* the A′ table in C9 and a reviewer-agreement figure are in
  `docs/curiosity/README.md`.
- [ ] **P5.3 — Three design-partner installs** (`WORKPLAN.md` 2.1a),
  after P0 and P1.1, with campaign mode, ten generations each.
  *Done when:* three rehearsal reports exist, each naming what broke.
- [ ] **P5.4 — The report from real data.** `REPORT.md` produced from
  the bench, the replay and the partners, linked from the README, with
  the paper's §7 metrics as numbers rather than definitions.
  *Done when:* every number in the README's first screen is generated.

### Phase 6 — trim (ongoing, one day at a time)

- [ ] **P6.1 — Generate the status.** One `harness/manifest.json` (module,
  status, test file) renders the README table and the ARCHITECTURE
  legend. The three hand-synced status locations collapse to one
  generated section and the tie-break rule is deleted. (F21)
- [ ] **P6.2 — Move history out of the way.** The revision logs in
  `Portable-Harness-Design.md` and the superseded arguments in
  `console/DESIGN.md` §2.1 go to `docs/history/`, linked, unchanged.
  The design documents keep only what is still a design.
- [ ] **P6.3 — Keep `learning/` as it is.** It is the product asset the
  first review named, and nothing in this plan touches it.

### Deferred, on purpose

- **The console (Tier 3)** waits on P3 and P5.3. Its value is a function
  of portability being true, and P3.1 gives most users the install
  without a web form.
- **Curiosity C3–C7** wait on P5.2's A′ verdict, as their own design
  insists.
- **A score that gates.** Principle 22b. Evaluators stay non-gating;
  P4.1 uses their delta to choose between candidates that already passed
  every gate, which is selection, not gating.

## 6. Sequencing, and what to measure at each step

| Weeks | Work | The number that should move |
|---|---|---|
| 1 | P0.1, P0.2, P0.3 | real generations: 0 → 1; install-to-rehearsal: hours → minutes |
| 2–3 | P5.1 (two repos first), P1.1, P1.2 | bench table exists; tests-pass rate on the bench, before and after P1.1 |
| 4–7 | P1.3, P2.1, P2.2, P5.1 (all five) | approval-and-pass rate v1 vs v2; largest repo that completes under cap |
| 6–9 | P3.1, P3.2, P3.3, P3.4 | CI systems: 1 → 2; `gh` dependency: removed |
| 8–11 | P4.1, P4.2, P4.3, P5.3 | candidates per generation: 1 → 2; generations per month on a quiet repo: 0 → ≥1 |
| 10–12 | P5.2, P5.4, P6 | every README number generated; A′ verdict recorded |

The one thing not to do is start P1.3 or P2.1 before P5.1 has two
repositories on it. An agentic executor and a scoped context are both
changes whose value cannot be seen on the fixtures the suite uses, and
building either without a bench repeats F20 at larger cost.

## 7. Risks in this plan

- **P1.3 widens the attack surface the reviewer must hold.** A tool loop
  reads files the allowlist forbids editing; that is intended, but every
  read is now an injection channel, so the fence `WORKPLAN.md` 5.9 built must
  wrap tool results as well as the source bundle, and the reviewer brief's
  injection clause must cover the tool log. Enforce in the parser, not
  the prompt.
- **P3.1 makes upgrades real, which makes breaking changes real.** The
  adapter schema in P0.3 needs a version field and the loader needs to
  refuse a newer schema than it knows, loudly.
- **P4.1 doubles implement and review cost per generation.** The budget
  cap bounds it; the bench says whether the second candidate pays.
- **The bench is a benchmark and will be optimised for.** Rotate a
  repository out every quarter and never let a bench repo's adapter be
  edited by the harness.
- **Twelve weeks is one person's twelve weeks.** Phases 1 to 4 are
  independent enough to parallelise across two people once P0 and the
  first two bench repos exist.
