# Workflow integration and evidence boundaries

This is the integration plan for the KPI design, not an executable workflow.
The current generation workflow remains unchanged by this documentation update.
The generated installation README is clarified so that operational reports are
not mistaken for independently verified KPIs.

## Current workflow and proposed attachment points

The copied workflow comes from
[`harness/templates/workflow.yml.tmpl`](../../harness/templates/workflow.yml.tmpl).
The shared workflow is generated by
[`render-shared-workflow.mjs`](../../harness/scripts/render-shared-workflow.mjs)
and called by a target repository at a pinned revision. Local rehearsal uses
[`rehearse.mjs`](../../harness/scripts/rehearse.mjs). A future collector must
use compatible run identities across these entry points.

| Stage | Evidence available today | Additional KPI work proposed |
| --- | --- | --- |
| Pause, validation, detection and reachability | Workflow outcomes and no-generation reasons | Inventory cycles that stop before assignment; record exclusions and infrastructure failures explicitly |
| Preflight and generation assignment | Baseline test results and a claimed generation identity | Join cycle to generation and record policy, model and base revisions |
| Suggest, rank, implement and refine | Proposals, attempt outcomes and spend summaries | Context selection provenance, repeated-idea adjudication and coverage of auxiliary model work |
| Tests inside the loop and review | Attempt tests and verdicts | Preserve and label every review decision on its exact patch revision |
| Quality evaluators | Non-gating baseline/post-change metrics and comparisons | Use task-appropriate acceptance evidence; a metric delta alone does not establish verified success |
| Guard and final tests | Checks against the changed tree | Link gate evidence to the assessed patch without letting a policy rewrite the assessor |
| Record persistence | Run records persisted even on unsuccessful assigned generations | Persist companion assessments and revisions idempotently; report missing evidence |
| PR read-back and optional deployment verification | PR disposition, revert information and configured deployment checks | Join these process events to follow-up; a merge or matching deployment is not evidence of user benefit |
| Operational report and run history | `<generationsDir>/REPORT.md` and `index.html` | Separate descriptive process statistics from the proposed verified KPI scorecard |
| Later observation | Project-specific external evidence can be supplied | Define acceptance criteria/windows, collect incidents and independently adjudicate outcomes |
| Strategy experimentation | No KPI-driven policy experiment pipeline installed | Compare pinned baseline/candidate policies, protect held-out evidence, review adoption and observe a bounded trial |

Record persistence and runtime evidence use always-run handling after a
generation number exists. That does not create generation records for every
preflight, validation or no-release stop. A future collector must preserve this
distinction rather than inventing successful or failed product changes for
cycles that never proposed one.

## What the existing report means

[`report.mjs`](../../harness/lib/report.mjs) computes operational release yield,
promotion precision and tokens per kept change from records where available.
[`run-history.mjs`](../../harness/lib/run-history.mjs) presents run fates.
A kept change is an approved, merged change not recorded as reverted; that is
different from meeting project acceptance criteria after adequate observation.
Promotion precision is about retention after landing, not the correctness of
review decisions. Before/after evaluator deltas describe their declared metrics,
not independent proof of overall product benefit.

Do not rename these measures to the five verified KPIs or backfill unknown
outcomes as successes. Add a separately labelled report only once its
assessment records exist. Its headline figures must expose coverage, pending
outcomes, denominators and incomplete spend.

## When executable workflow changes become justified

1. Implement and test stable provenance/evidence collectors over existing records.
2. Add independent outcome and per-review assessments, including revisions and
   late incidents, with project-specific acceptance criteria.
3. Implement a read-only aggregator that handles missing evidence and reconciles
   totals. Initially run it manually on a bounded cohort.
4. Wire non-gating collection/reporting into copied, shared and rehearsal paths;
   compare their failure, pause and no-generation behaviour. Never make a missing
   assessment imply success or change a product gate.
5. Only then trial an experiment runner with isolated policy worktrees, protected
   held-out labels, full-system budgets and explicit rollback criteria.

Behavioural workflow changes require regression tests and regeneration of the
shared workflow from its source template where applicable. Generated YAML and
its source must agree. Do not add a scheduled KPI optimiser or new model calls
simply because a design document exists.

## Policy adoption and authority

The harness can propose operating-policy changes through the existing review
route. It may not expand editable paths, weaken tests, rewrite hidden assessment
labels or bypass the configured approval class. New installations remain PR-only
by default; autonomous merge remains an explicit configuration choice.

Use [the experiment template](templates/experiment.template.md) to predeclare
hypotheses, cohorts, budgets and acceptance thresholds. A scorecard supports a
decision; it is not permission to change the evaluator or ship a policy.
